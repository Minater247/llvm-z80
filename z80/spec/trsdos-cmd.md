## 1  Introduction <a name="1-introduction"></a>
The **/CMD** file format is the load‑module and executable container used by TRSDOS 6 and its derivatives (LDOS/LS‑DOS).  A /CMD file consists of a sequence of variable‑length *records* that collectively describe the binary image, metadata and (optionally) directory structures required by the TRSDOS system loader.  This document consolidates the historical format defined by Logical Systems Inc. with modern terminology, C‑language structures, endianness considerations and validation advice.  It is modelled after the style of the ELF specification for consistency and ease of comprehension.  

Historic content is derived primarily from Roy Soltoff’s “Roy’s Technical Corner” column in **The LDOS Quarterly** (Vol 1 No 4, 1982) ([tim-mann.org](https://www.tim-mann.org/trs80/doc/ldosq1-4.pdf)) and from the *Programmer’s Guide to LDOS/TRSDOS Version 6* ([tim-mann.org](https://www.tim-mann.org/trs80/doc/prgguide.pdf?utm_source=chatgpt.com)).

## 3  Overall File Organisation <a name="3-overall-file-organisation"></a>
A /CMD file is a **flat, sequential stream** of *records*; no global header or directory precedes the first record.  The loader reads records until it encounters a **Transfer Address (type `0x02`)** or a **End‑of‑Member (type `0x04`)** record, at which point execution or specialised processing begins.  Ordering of records is flexible; load blocks (`0x01`) may appear in any order, enabling simple relocation‑free overlays.

```
+-----------+-----------+-----------+-----+
| Record #1 | Record #2 |  …  | Record #n |
+-----------+-----------+-----------+-----+
```

## 4  Record Header Structure <a name="4-record-header-structure"></a>
Every record begins with a *Record Header*:
```c
typedef struct __attribute__((packed)) {
    uint8_t  type;   /* Record type identifier */
    uint8_t  len;    /* Length of DATA field in bytes (1‑256) */
    uint8_t  data[]; /* Payload, semantics depend on `type` */
} cmd_record_t;
```
* The `len` field value `0x00` represents **256** bytes.  Consequently, the maximum data field length achievable is 256 bytes.
* For **Load Block** records (`type 0x01`), the first **two** bytes of `data` hold the 16‑bit load address, and therefore *subtract* from the usable payload length (see § 5.1).

## 5  Record Types <a name="5-record-types"></a>
### 5.0  Summary Table
| Type | Mnemonic | Typical `len` | Data Field Purpose | Notes |
|------|----------|---------------|--------------------|-------|
| `0x01` | **LOAD** | 3‑256 | `u16` load   addr + object bytes | Lengths `0,1,2` → 254‑256 payload bytes ([tim-mann.org](https://www.tim-mann.org/trs80/doc/ldosq1-4.pdf)) |
| `0x02` | **XFER** | 2 | `u16` entry point | Loader begins execution here |
| `0x04` | **EOM**  | 1 | `0x00` | Terminates PDS member when loader expects one |
| `0x05` | **HDR**  | ≤8 | ASCII module name | First record of plain /CMD |
| `0x06` | **PDSHDR** | Varies | PDS metadata | Used only by PDS utilities |
| `0x07` | **PATCH** | ≤8 | Patch label | Loader may map symbolically |
| `0x08` | **ISAM** | 6 | ISAM dir entry (see §5.7) | Library support |
| `0x0A` | **EODIR** | 1 | `0x00` | End of ISAM directory |
| `0x0C` | **PDSDIR** | 11 | Member dir entry | Name + date/meta |
| `0x0E` | **EOPDS** | 1 | `0x00` | End of PDS member dir |
| `0x10` | **YANK** | As `0x01` | Deprecated load block | Marked for removal |
| `0x1F` | **COPYRIGHT** | 1‑255 | Free‑form text | Auto‑generated by `COM` pseudo‑op |

> **Implementation Note** — Record codes above `0x1F` are *invalid*; codes in the range `0x11‑0x18` are reserved for future *relocatable* records ([tim-mann.org](https://www.tim-mann.org/trs80/doc/ldosq1-4.pdf)).

### 5.1  Load Block (`type 0x01`)
```c
typedef struct __attribute__((packed)) {
    uint8_t  type;   /* 0x01 */
    uint8_t  len;    /* (payload + 2) % 256 */
    uint16_t addr;   /* little‑endian load address */
    uint8_t  payload[len_minus_2];
} cmd_load_t;
```
* **Length Encoding**: Values `0x00`, `0x01`, `0x02` indicate 254‑256 bytes of payload after the address, allowing a full‑sector load.  The loader decrements `len` by **2** internally before copy.
* Payload bytes are copied verbatim to RAM beginning at `addr`.

### 5.2  Transfer Address (`type 0x02`)
Contains a single `u16` entry point.  Upon encountering this record, the loader *immediately* jumps to the supplied address unless chained loading is requested.

### 5.3  End of Member (`type 0x04`)
Used primarily within **Partitioned Data Set** (PDS) files to delimit sub‑modules.  Stand‑alone loaders may ignore it; when unexpected it constitutes a *format error.*

### 5.4  Module Header (`type 0x05`)
A human‑readable identifier (traditionally up to 8 ASCII bytes, space‑padded).  Not interpreted by the loader beyond length traversal, but utilities display it.

*Example* (`LS 'LBASIC/CMD'` first record):
```
05 06 4C 42 41 53 49 43  ; "LBASIC"([tim-mann.org](https://www.tim-mann.org/trs80/doc/ldosq1-4.pdf))
```

### 5.5  Copyright (`type 0x1F`)
Free‑form text, UTF‑8 or ASCII, with a recommended maximum of 80 bytes.  Generated automatically by the `COM` pseudo‑op in **EDAS** assembler.

### 5.6  PDS‑related Records (`0x06`, `0x08`, `0x0A`, `0x0C`, `0x0E`)
Partitioned Data Sets emulate IBM OS/360 libraries.  See the LDOS Technical Reference for full triad pointer semantics.  Modern tooling rarely needs to emit these records; however, linkers should preserve them when updating existing libraries.

### 5.7  ISAM Directory Entry (`type 0x08`)
```c
typedef struct __attribute__((packed)) {
    uint8_t  entry_no;      /* ISAM ordinal supplied on SYS1 command line */
    uint16_t transfer_addr; /* alternate entry point */
    uint24_t triad_ptr;     /* NRN<<16 | RBO */
} cmd_isam_t;
```

## 6  Loader Behaviour <a name="6-loader-behaviour"></a>
1. **Initialisation**: Optionally verify first record is `0x05`.  Non‑fatal.
2. **Record Loop**:
   * Read `type`, `len`; treat `0x00` as `256`.
   * Switch on `type`:
     * `0x01`: copy payload to memory at `addr`.
     * `0x02`: set `entry_point=payload16`; *stop parsing*.
     * `0x04`: `break` (PDS end).
     * Unknown / reserved: **format error**.
3. **Execution**: If `entry_point` defined, `JP entry_point`.

Pseudo‑C implementation is provided in § 8.

## 7  Validation & Error Handling <a name="7-validation--error-handling"></a>
| Check | Failure Handling |
|-------|-----------------|
| `len == 0` ⇒ 256 bytes only for `type 0x01` | Reject otherwise. |
| Overlapping load blocks | Warn; last write wins (TRSDOS behaviour). |
| Multiple `0x02` records | Use first; ignore subsequent. |
| File ends mid‑record | Fatal error. |

## 8  Reference Implementations <a name="8-reference-implementations"></a>
Complete, liberally‑licensed sample code can be found at **Jim Lawless’ readcmd** repository ([jimlawless.net](https://jimlawless.net/blog/posts/trs80-cmd/)).  A simplified parser skeleton:
```c
bool load_cmd(FILE *fp, uint16_t *entry) {
    while (true) {
        int t = fgetc(fp); if (t == EOF) return false;
        int l = fgetc(fp); if (l == EOF) return false;
        if (!l) l = 256;
        switch (t) {
        case 0x01: {
            uint16_t addr = fgetle16(fp);
            for (int i=0;i<l-2;++i) mem_write(addr+i, fgetc(fp));
            break; }
        case 0x02:
            *entry = fgetle16(fp);
            fseek(fp, l-2, SEEK_CUR);
            return true;
        default:
            fseek(fp, l, SEEK_CUR);
        }
    }
}
```

## 9  Worked Example <a name="9-worked-example"></a>
The minimal *fill‑screen* program (15 bytes of Z‑80 code) packaged as a /CMD file:
```text
01 11 00 6C 21 00 3C 3E BF 77 11 01 3C 01 FF 03 ED B0 C9
02 02 00 6C
```
*   First record (`0x01`): `len=0x11==17` → 15 payload bytes after 2‑byte load address `0x6C00`.
*   Second record (`0x02`): transfer to `0x6C00`.
Verified via **readcmd** output and executed under `trs80gp` emulator ([jimlawless.net](https://jimlawless.net/blog/posts/trs80-cmd/)).

## 10  Future‑Reserve & Relocatable Records <a name="10-future‑reserve--relocatable-records"></a>
Record codes `0x11` through `0x18` are reserved for a potential **Relocatable CMD** extension that would embed relocation information analogous to ELF `R_*` entries.  Until a formal proposal is ratified these codes **MUST** be treated as errors by strict parsers.
